# 首星玩家视角实测

## 11 月 19 日新增观察与后续方案

Windows、Godot 4.7.2、RTX 4060、540×960，工作区基准 `e756164`，含当时的本地改动。种子 4416584 完成一座回彩碑，领取暖霆羊，前往第二座途中护心耗尽。旧版三节点通关和下文修复专项各有独立记录。

**后续试玩方案（待执行）**

1. 开局前设好本局路线和奖励偏好。低护心优先可用回复，健康时优先攻击；完成三碑、拿到三份奖励后追踪首领。脚本持续执行走位与避险。
2. 建议每 30 秒集中看一次最近画面和变化摘要，包括护心、守卫数量、目标距离以及上次动作。阶段截图入队，普通奖励沿用当前策略；观察者随时调整下一个选择。
3. 守卫数长时间不变且距碑持续扩大时，先自动回到附近并保留前后画面。反复无进展、当前面板无法识别、路线和 HUD 计数不一致时再请求判断。同一异常合并一次，提供刚才做过什么、做完是否改善。
4. 单次验收保留种子、三份奖励确认、三碑进度、首领战和胜利帧。分别统计等面板时间、无进展时间、人工介入次数和剔除截图扰动后的帧耗。旧脚本曾因界面“节点”改称“回彩碑”漏认领奖，需先用既有截图回放验证新旧文案。

## 修复版回归

同一 Windows 工作区、Godot 4.7.2 Compatibility、RTX 4060，基准提交 `15fdbee5948abc7d4c8945b2213b04e6448ce6cb`。专项目标是在其他小节点旁手动追踪最终节点，接近后辨认正确的石碑，并验证建筑两侧的攻击边界。[回归脚本](../../../src/game/full_game/node_guidance_test.gd)

- 360 和 540 宽度均验证了顶部距离、屏外箭头、屏内标记、3 米站位圈和独立的附近倒计时。按 5、6、1 的顺序开启，三次领取伙伴后进入首领战。守卫从队列转为活敌时计数连续，剩一名时仍有头标，杂兵存活不阻止结算。此专项通过测试伤害接口击败敌人，仅验证流程。[追踪主碑](首星实测证据/修复后主碑.png) · [最后一名守卫](首星实测证据/修复后守卫.png)
- 敌人隔着景观碑无法起手，绕到开阔处可发动攻击。躲到碑后的目标不受伤，预警网格的相应区域留空。另在实际危险带上固定镜头，比较开关前景淡出时脚边 110×90 像素的同一块区域，显示危险带引起的变化从 189 像素增至 552 像素。无窗口专项 51 项、GPU 专项 57 项通过。[脚下危险带](首星实测证据/修复后预警.png)
- 封面开始按钮注入触摸，记录到第一张战场 `frame_post_draw`，该窗口内不截图。修前复现 1957 毫秒，埋点中春景网格生成占 1305 毫秒。修复后同机五次分别为 567、544、546、559、487 毫秒。草团球面保留原三角面及正反面，改用共享顶点和索引；敌人染色面积表只扫描每帧非透明包围框。可用 `godot --path src/game --script res://full_game/node_guidance_test.gd -- --measure-click` 复测，每次重启进程。开发中第一次更换着色器的过渡版本曾测到 2489 毫秒，最终五次未清驱动缓存。修复版长战斗帧耗、全新驱动缓存和手机仍待复测。下节保留修复前战斗的原始与剔除截图数据。

同时运行的旧综合脚本存在未通过项。`node_interaction_test` 仍期望点击开战，`ui_test` 与 `rules_test` 访问已移除的控件或接口，`formal_assets_test` 的伙伴攻击图集断言失败，`overhead_labels_test` 的两条伙伴星级绘制顺序断言失败。当前开启条件另由 51 项自动开启专项覆盖。

## 2026-11-18 桌面渲染窗口

正式版工作区基准 `15fdbee`，含既有本地修改。Windows、Godot 4.7.2、OpenGL Compatibility、RTX 4060、540×960。使用普通玩家摇杆与面板，按屏幕目标游玩；截图做中文 OCR，另录启动埋点与渲染回调间隔。以下属于程序操控的观察，真人手感和手机表现待验。

| 现象 | 复现与影响 |
| --- | --- |
| 手动追踪和顶部距离各指一个节点 | 雨林湖泊完成 6、5、4 号节点，在地图选距 75 米的最终节点。边缘指示变为「空环蚀核 · 可唤醒」，顶部仍显示「小节点 3」「距节点 33.1 米」。跟顶部距离会走向另一场战斗。[地图](首星实测证据/追踪前.png) · [游戏画面](首星实测证据/追踪后.png) |
| 守卫战难判断清场进度 | 提示明确说明普通敌人继续出现，顶栏仅显示节点编号与「战斗」。混战时难从画面判断还剩哪只守卫。[战斗画面](首星实测证据/守卫战.png) |
| 障碍物和摇杆遮挡关键信息 | 高石碑挡住角色、附近敌人和脚下预警的局部；角色描边仍在。浮动摇杆移到中央偏下时，会盖住 Boss 击败后的提示。[开启倒计时](首星实测证据/最终节点.png) · [击败提示](首星实测证据/Boss击败.png) |

其中一局完成 5、6、1 号节点，选了三次伙伴，4 只伙伴到达最终节点。剩 1 点护心、开启倒计时 1.6 秒时受到攻击，随后结算。另一局完成六个小节点后出现 Boss 击败提示。两次结果独立记录。

三节点局三场守卫战剔除面板及截图扰动窗口后，帧间隔 P95 依次为 16.73、16.73、16.74 毫秒，最大值 38.25、49.39、33.70 毫秒。原始战斗窗口 P99 为 51.70、64.54、86.22 毫秒，同步保存 PNG 会放大尾部延迟。逐场样本量、原始与过滤后统计见[数据](首星实测证据/战斗帧耗.json)。过滤覆盖截图开始前 18 毫秒至写完后 70 毫秒及与之相交的帧。结果仅覆盖本机首星。

## 运行与观察

以下命令记录历史本机工具的操作方式。用户确认整体测试流程尚未完善，`tools/自动试玩/` 仅在本机保留，未纳入仓库；不能直接按仓库内容复现本节工具流程。

在 Windows 上安装 Python 3.10+、NumPy、OpenCV（`opencv-python`）和中文 Windows OCR，使用已导入资源的正式版工程及 Godot 4.7.2。仓库根执行 `python -B tools/自动试玩/run.py`。可用 `--godot` 指定引擎。工具在 `_local/自动试玩/<时间>/run-XX/` 隔离每局的存档、日志、截图和性能 CSV。启动器输出本次目录。默认每局活动时间上限 420 秒，死亡后最多尝试三局。

工具每约十秒保存现场图，也保存阶段画面。当前原型按偏好处理强化，伙伴或最终路线默认给观察者 5 秒覆盖窗口（`--review-seconds` 可调），到时采用建议选项。可用 `--prefer "<本局目录>" <强化名>` 预设强化，`--prefer-partner "<本局目录>" <卡片关键词>` 预设伙伴，或在当前请求有效时用 `--choose "<本局目录>" <决定编号> <选项序号>` 指定选择。观察者及默认策略的选择写入 `events.jsonl`，独立回归使用 `--auto`。已观察到提前指定强化生效、伙伴等待期结束自动领取；最新工具的三碑通关、伙伴预设及异常汇总仍待验证。

窗口探针（仅本机保留，未入库：`tools/自动试玩/窗口观察.gd`）读取已显示的界面文字、可点击卡片及角色周围的画面，发送普通触屏按下、拖动和松开事件。玩家策略（仅本机保留，未入库：`tools/自动试玩/player.py`）从目标距离变化估算方向，避险（仅本机保留，未入库：`tools/自动试玩/steering.py`）从屏幕颜色、预警轮廓和敌人外形选方向。中文字形 OCR 在游戏退出后批处理，用于复核截图。逐帧 CSV 保留相邻绘制回调间隔、图像回读耗时、绘制调用和视口 CPU/GPU 耗时；窗口回读仍会影响性能。

### 试玩流程复核

旧脚本在决策链上同步保存整张 PNG、做 OCR 并多次松杆。三节点局 317 张战斗图之间的中位间隔为 465 毫秒，单图保存中位约 44 毫秒。奖励和阶段切换还需临时接管。新驱动持续按住摇杆，在同局获得三次伙伴奖励后追踪首领。第一次正常击败首领，却因报告额外等候出发按钮而超时。修正胜利条件后的独立回归由程序完成 1、2、3 号节点并击败首领，记录了 3280 次画面观测，控制周期中位 100 毫秒、决策耗时 P95 为 0.97 毫秒，保存 24 张关键截图并以状态 0 退出。[击败画面](首星实测证据/三节点击败.png) · [本局统计](首星实测证据/自动通关.json)

工作区在复跑期间已有 HUD 变化。后续实测可读到带距离的追踪目标、「节点守卫剩余」及顶部战斗提示。上表保留早期画面的复现条件。
